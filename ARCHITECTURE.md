# Connect (Tealbrick mini app): architecture

State: verified against the repo on 2026-10-17. Claims cite paths in this repo. Anything not verified is marked UNVERIFIED. For the whole system see the system `ARCHITECTURE.md` and `SYSTEM-OVERVIEW.md`.

## Common app pattern (verified for this repo on 2026-10-17)

- **Runtime**: Node 24, TypeScript run through `tsc` to `dist/`, UI built by `scripts/build-ui.ts` (no bundler). Connect writes a flat `dist/ui/`; it does not adopt the template's content-hashed `assets-<hash>/` directory (header of `scripts/build-ui.ts`). The app is started by `startApp` from `@opt2-tealbrick/miniapp-sdk` (`src/main.ts`).
- **Dockerfile**: two stages on `node:24-slim` pinned by digest, `pnpm install --frozen-lockfile --ignore-scripts`, `pnpm run build && pnpm prune --prod`, the manifest also copied to `/opt/tb/tealbrick.manifest.json` (the `tb-exec` default), `USER node`, no `VOLUME`. The SDK drops root to uid 1000 itself when the platform starts the container as root (Railway volumes are root-owned).
- **Data**: one SQLite file `TB_DATA_DIR/app.db` owned by the SDK. App tables use their own prefix; SDK tables use `tb_*`. On Railway there is ONE volume per service: the backup directory is `<data mount>/backup`, so the volume size is data plus backup (C28).
- **Migrations**: `migrations/NNNN_name.sql` (or `.ts` exporting `up(db)`). The SDK enforces forward-only: gap-free from 0001, one transaction each, sha256 recorded in `tb_migrations`. A changed, missing, misnamed or `down` migration stops the app with `migration_invalid`.
- **Backups and restore**: SDK cron runner writes `tb-backup-<UTC>.tar.gz`; export `tealbrick.export/1` never carries the instance key, KEK, keys, secrets or sessions. Restore at next boot with `TB_RESTORE_FROM`.
- **Authorization**: the bridge gates (`gate()`); the SDK decides (`authorize()`): run, hold or refuse. Holds and receipts live in the app's own `tb_receipts` table. Raw call input is never stored, only a digest.
- **Manifest** `tealbrick.manifest.json` is the only source for operations, scopes, settings, hooks, companions, skills, runtime hints, backups and UI paths. Schema `tealbrick.miniapp/2`, `sdkMajor 1`, `source.license Apache-2.0`. Agent ops become MCP tools `<product>__<op>`. Person ops are owner UI only.
- **Generated**: `gen/` (openapi, kit, docs, railway) is produced by `tb-gen` and is not committed. The typed client kit is built into `dist/kit` and imported as `#kit` in apps that have one.
- **Standard UI pages** (from the kit `AppShell`): Holds, Receipts, Agents and scopes, Keys (where the app has keys), Backups and export.
- **Licence files**: `LICENSE` (Apache-2.0), `NOTICE`, `THIRD_PARTY_NOTICES.md`. The brand mark and app art are Tealbrick artwork and are not Apache-licensed.
- **Private by design**: no public address. Only the bridge is public.

## Connect: what it does

Connect is the one place for outside connectivity (C16 and the PRD). Per connected account the owner sets a tier: read, read/update, read/update/delete. Both kinds exist: "as me" (the agent uses the owner's account) and "as itself" (the agent's own identity, for example its Buzz identity). Tools are dynamic: search, then call. A send to a new recipient answers `first_contact_required` and the agent calls the `__first_contact` variant, which is held.

## Operations (from `tealbrick.manifest.json`)

55 operations.
- Read (agent): `tools` (dynamic, per account), `accounts_list`, `buzz_identity`, `buzz_channels`, `buzz_read`, `identities_list`, `buzz_scheduled`, `channel_inbox`, `channel_conversations`, and the apps-only data family `data_accounts_list`, `data_catalog`, `data_pull`, `data_lease` (listed with agent audience until the audience `app` exists, G-1; the handlers refuse every caller that is not an app).
- Write (agent): `buzz_schedule_cancel`.
- Outward, hold family `outward`: `buzz_post`, `buzz_dm`, `buzz_react`, `buzz_edit`, `buzz_schedule`, `channel_send`, `channel_reply`, `channel_dm`, `channel_edit`, `channel_react`.
- Outward, hold family `first_contact`: `buzz_dm_first`, `channel_dm_first`.
- Destructive, hold `destructive`: `buzz_delete`, `channel_delete`.
- Person: 10 reads (`services_search`, `accounts_overview`, `data_leases_list`, ...), 16 writes (`account_connect`, `account_app_share`, `database_account_connect`, `data_lease_revoke`, `catalog_account_connect`, `mcp_account_connect`, `buzz_identities_generate`, `channel_account_connect`, `sender_identity_set`, ...), and `buzz_profile_publish` (outward, hold family `identity`).
- Dynamic tools resolve per tool to read, write, outward, destructive or money. Unknown verbs classify fail-CLOSED (write or outward; payment is money, always held) (SEC-02). Hold view binding for send tools: account, recipients or channel, subject, first 500 characters as plain text, attachment names and sizes (`src/hold-view.ts`, C201).
- CRUD per tool (C276a): catalog ops by method — POST on a listed collection `[create]`, PUT/PATCH `[update]`, DELETE `[delete]`; a POST on an item path, with an action word, or on a path with no GET stays `[create, update]`; an op-level `x-tealbrick-crud` wins. Composio/MCP names: CREATE/ADD/INSERT → create, UPDATE/SET/PATCH/EDIT → update, DELETE/REMOVE → delete, anything else `[create, update]`. Read and money never change, destructive keeps delete, effect and hold family never change (`withCrud`, `src/effect.ts`). Stored tool rows are re-made on start when the classifier or catalog version changes (`src/tool-resync.ts`, table `connect_meta`, migration 0014). Snapshot of every catalog op: `test/fixtures/catalog/classes-<version>.json`.
- Catalog HTTP (0.6.2): the declared JSON media type is sent (CF-CT-1); WebDAV `x-propfind`/`x-mkcol`/`x-copy`/`x-move` are compiled (PROPFIND read with Depth ≤ 1; MKCOL/COPY create; MOVE the destructive class); MOVE/COPY send `Overwrite: F` and a `Destination` built from `x-destination-template` under the same origin, prefix and user root, with the multi-segment guards of CF-NC-2.
- Catalog sends (C276c): an entry's `firstContact` labels outward ops that email or message people and says where the recipients are in the input (`body.to`, ...). They go through the X-02 first-contact check like `GMAIL_SEND_EMAIL`; `[]` (the recipient is stored data, e.g. a ticket's customer) makes every call a first contact. Entry `credentialHint` is shown in the connect form.

## Scopes, hooks and companions

- **Scopes:** One scope type, `account` (access `read`, `read_update`, `read_update_delete`, `apps_only` which agents cannot use). Default grant: shared maps to `apps_only`.
- **Hooks:** None.
- **Companion grants it asks for:** None asked. Other apps call Connect: Inbox calls `buzz_dm`, `buzz_dm_first`, `channel_dm`, `channel_dm_first`; Fleet calls `identities_list`.

## Data operations for apps (R3, unreleased)

One generic contract for Knowledge (foundry) and Observer (FOUNDRY-DESIGN v2 section 3.4, decisions C230 and C169). A new dataset is a new entry in `data_catalog`, not a new operation.

- **Operations:** `data_accounts_list {}`, `data_catalog {account}`, `data_pull {account, dataset, direction?, cursor?, since?, until?, limit <= 200}`. Effect read, crud read, idempotency none, no receipt, no scope type: a companion grant needs `crud: ["read"]` only. Every caller that is not an app (an agent, a person) gets `no_access` (403).
- **Sharing:** the owner (person operation `account_app_share {account, product, instance, level}`) shares one connected chat account with one installed app: `none` (default), `available` (`data_catalog` only: dataset names, kinds, approximate counts, conversation names, history flag; no message) or `shared` (`data_pull` too). Apps: Knowledge and Observer (`src/data/shares.ts`). **Binding (C240, migration 0013):** the share stores the verified product AND the instance id the owner picked, from `ctx.companionCallers()` (person ops, miniapp-sdk 0.1.32 / spec 0.1.48: the app instances of the current signed slice, with `provider`). An instance not listed for that product is refused `app_instance_unknown` (404), no instance `instance_required`; an SDK without the function lists nothing, so no share can be made (fail closed). An app sees only accounts shared with its product AND its instance (`ctx.caller.id`, the verified grant subject); a reinstalled app (new instance id) needs a new share (one row per account and app: one instance per app), on every data call the caller must STILL be listed under its product in the current signed slice (`ctx.caller.listed`, sdk 0.1.32; C240 call-time check): `false` is refused `share_instance_gone` (403, audited) even with a valid grant `prd`, no flag (older SDK) `companion_list_unavailable` (503, fail closed), both retryable after 30 s (slice lag); an app with no bound share still gets the plain `not_found` / empty list; the page shows such a row as removed ("it can no longer read", level read-only, "Stop sharing", an explicit move button that names an own-server target), and a row from before 0013 (no instance) serves nobody (Accounts: "Share again" on the row plus one page notice with the count). Nothing is bound on a first call. `accounts_overview` returns `dataApps[].instances` (`provider`, `ownInfra`) and per share `instance` and `current` (the instance is still listed); the page names an `own_infra` target (S3-4 residual). Every account the app cannot see (unknown id, not a chat account, not connected, shared with another app, unknown app) answers the identical `not_found`. `available` with `data_pull` answers `scope_denied`. Disconnecting an account removes its shares. A share records `set_at`: `data_pull` returns only messages Connect received at or after it, unless the owner chose `includeHistory` (the whole 30-day log). `account_app_share` has a receipt; every data call (`data_accounts_list`, `data_catalog`, `data_pull`) writes one audit line, refused calls too (op, outcome = `ok` or the refusal code, caller type and id, verified product or null, account and dataset as named, row count, quarantined count; never text).
- **Database accounts (C336 RQ-3, 0.6.4):** see the next section. `data_accounts_list` and `data_catalog` also answer database accounts shared with the caller; `data_pull` on a database answers `delivery_lease` (400) after the share check.
- **Which product calls:** the identity is the VERIFIED caller product (`ctx.caller.product`, miniapp-sdk 0.1.28 / spec 0.1.46: the `prd` claim of the verified companion grant, else the product id of the Portal-signed slice entry for the calling instance; a grant/slice mismatch is refused `grant_invalid` by the SDK), never the manifest name (any installed app can carry any name; Coordinator ruling). `verifiedAppProduct` (`src/data/caller.ts`) is the only reader. Fail closed: an app caller without a product is refused `caller_unverified` (403); a person or an agent is refused `no_access` (403). There is no fallback to `ctx.caller.name`, the manifest name, the instance id or an input field. The share check (`connect_account_shares`), the share record and the audit row (`connect_data_audit.product`) all key on the product id. `ctx.caller.name` is a display label only. Tests build app callers with a `product` (the shape the SDK produces) and `test/data-caller-e2e.test.ts` runs the real SDK with a signed slice.
- **Dataset `messages`** (kind messages, delivery pull, contract `messages/1`): rows from `connect_channel_inbox`. The pull order is `rev` (a new message, an edit or a deletion takes the next number, so a forward cursor sees changes to rows it already passed). Cursors are opaque and stable: `rev` is a per-account sequence and a cursor names its account, so other accounts' traffic never moves it and it is refused on another account. Forward gives newer rows, backward older rows (newest first). `exhausted` ends a pull; a forward cursor stays valid after `exhausted` for polling. `anchor` (first page only) is the cursor of the newest row. `retryAfterS` is the answer of a rate-limited source (none in phase 1). Page: at most 200 rows and 2 MiB. Text is cut at 65 536 characters (`truncated`), attachments are metadata only, at most 32 (`attachmentsTruncated`), a deleted message has empty text. `author.handle` is `<channel>:<value>`: canonical (`normalizeHandle`) for slack and telegram, raw for teams and discord. `author.kind` is `bot` when the provider says the sender is a bot (Slack `bot_id`, Discord `author.bot`, Telegram `from.is_bot`, Teams role bot), `self` for the connected bot's own id, else `person`; bot rows are stored only while the account has an app share (otherwise dropped as before) and never reach agents (`channel_inbox`, first-contact checks); `channel_inbox` moves `nextSeq` past hidden rows (bots, deleted messages). `untrusted` is always true.
- **Quarantine:** a stored row that does not conform to `messages/1` is skipped, counted (`quarantined` on the answer and in the audit line) and logged with its account and rev (never its text); the page stays valid and the cursor moves on, so one bad row never blocks the account.
- **Validation:** every page is checked against the vendored schema (`validateAgainstSchema` of `@opt2-tealbrick/manifest` 0.1.19) before it leaves; a mismatch answers `data_contract_violation` (500) and a log line with paths only, never a page.
- **History in phase 1:** none of the four providers has a history reader in Connect. The inbound log is the only record (30 days; apps need 7), so the catalog says `history: false` and a backward pull answers `exhausted: true` with no rows. A provider with `readsHistory: true` pages backward through the log. Telegram bots are live-only. Slack, Teams and Discord could add a reader later without a new operation. Buzz is not a connected account and is not in phase 1.
- **Edits and deletions:** read from Slack (`message_changed` with `edited`, `message_deleted`), Discord (`MESSAGE_UPDATE` with `edited_timestamp`, `MESSAGE_DELETE`, `MESSAGE_DELETE_BULK`) and Telegram edits (`edited_message`, `edited_channel_post`); Teams `messageUpdate` / `messageDelete` are parsed too. A change takes a new `rev`, is ordered (an older or repeated edit changes nothing) and applies only to a message that is in the log: an edit or deletion of an unlogged message (older than the retention, from before the bot connected) is an orphan, dropped, counted in `unmatched_changes` and logged as metadata, so an agent never sees an edit as a new message. `data_catalog` says per provider whether it reports `edits` and `deletions`, and says true only where every path is wired: Slack and Discord both, Telegram edits only, Teams neither (Teams sends the activities only in some installations). Where `deletions` is false, **a deleted message keeps its text for apps until the 30-day purge.** The same holds for a deletion that happened while the provider was not sending events. Attachment metadata is supported by the log and the contract; no provider fills it yet.

## Database accounts and data leases (C336 RQ-3, 0.6.4)

FOUNDRY-DESIGN §3.3-3.4 and SPEC-REQUESTS-C336 RQ-3. Knowledge taps a supported data source directly through a grant from Connect (C330(3), C325). Postgres only; MySQL is the next kind and needs one driver in `DatabaseDrivers`, one query set next to `POSTGRES_SQL` and an entry in `DATABASE_KINDS` (`src/data/database.ts`).

- **Account:** person op `database_account_connect {label, host, port?, database, user, password, sslmode?}`. The DSN is SEALED in `ctx.secrets` under `db:<id>` (ids `cdb_<ULID>`). The table `connect_db_accounts` keeps the label, the kind, a display string `host:port/database` (no user, no password) and the state. Agents never see it: no scope instance is created, so `accounts_list` is empty of it, and no dynamic tool exists for the service `postgres`. The host goes through `resolvePublicHost` (`src/util/net-policy.ts`, the same rules as `assertEndpointAllowed`): private, loopback, link-local, CGNAT, ULA, local names and any private DNS answer are refused (`endpoint_not_allowed`, 422). The only exception mechanism in Connect is the exact-origin allow list for tests (`catalogAllowOrigins`, `allowRelayOrigins`); no owner-facing exception exists (C41), and the database equivalent is `databaseAllowHosts`, set by tests only. A form is checked before anything is stored: Connect connects once and refuses a superuser or a replication role (`database_role_too_powerful`). `sslmode`: `verify-full` (default), `require` (encrypted, no certificate check), `disable`.
- **What Connect sends to a customer database:** only the fixed statements in `POSTGRES_SQL` (the role flags; `information_schema.columns` and `pg_class` for names, types and `reltuples`). No input is put into them, no table is read. The production client (`src/data/pg-driver.ts`, `pg` 8.23.1) connects to the ADDRESS the policy checked (TLS keeps checking the host name), with a read-only session, time limits and no PG* environment or `~/.pgpass`. Tests pass a fake driver and assert that only those statements ran. A driver failure becomes `database_unreachable` with fixed text and an allow-listed error code; a driver message (which can name a user or host) is never forwarded.
- **Sharing:** `account_app_share {account, product, level, instance, route?}` works on a `cdb_` account as on a chat account (binding to the verified product and instance, C240). Shares live in `connect_db_shares` (same shape as `connect_account_shares` plus `route`). `route` is `direct` (default) or `via_observer`; `via_observer` is only valid for Knowledge, and a share with it gives that product nothing (not listed, `not_found` everywhere), Observer reads through its own `direct` share. Changing the level, route or instance, removing the share, or disconnecting the database ends the open leases of that share.
- **Catalog:** `data_catalog` of a database lists `schema.table` datasets (kind `table`, delivery `lease`, `relation` table, view or foreign_table, `approxRows` when the database has statistics, `columns`). At most 2000 tables and 500 columns per table; a name that cannot be written as `schema.table` is left out.
- **`data_lease {account, datasets[1..50], ttlS?<=900}`:** apps only (`dataCaller`), account shared at `shared` with route `direct` to the verified product AND instance that is still listed, every dataset in the catalog right now (`dataset_not_found` 404 otherwise). `ttlS` default 300; above 900 `ttl_too_long`. Answer `{leaseId, kind, host, port, checkedAddress, database, user, password, sslmode, datasets, expiresAt}`. `checkedAddress` is the address the policy checked now; connect to it with TLS name `host`. Manifest: crud read, effect read, idempotency none, receipt false, audience agent, no scope type, not dynamic (M-OP-11 of spec 0.1.66). The `secretOutput` flag is not in the manifest: the pinned spec 0.1.52 refuses the field. Add it when the spec pin moves.
- **Lease record and audit:** `connect_data_leases` (lease id, account, product, instance, datasets, issued, expires, revoked). It never holds a credential. The data audit line (`connect_data_audit`, new nullable columns `lease_id`, `lease_expires_at`) records the lease id, account, datasets, expiry and caller (type, id, verified product). A lease whose audit line cannot be written is withheld (`audit_unavailable` 503) and ended. The password appears in no log line, receipt, record, owner list or error text (canary test `test/database-lease.test.ts`).
- **v0 limit:** a lease is the owner's sealed read-only credential plus the expiry Connect records (no per-lease database role). Ending a lease (`data_lease_revoke`, or a changed share) ends it in Connect and in the lists; the password stays valid at the database until the owner changes it there. Page, README and manifest say so. A per-lease role (CREATE ROLE ... VALID UNTIL) needs a privileged admin credential and is a later step.
- **Owner ops:** `data_leases_list` (newest 100: app, database, datasets, issued, ends, state active/revoked/expired; no credential), `data_lease_revoke {lease}` (receipt), `data_access_log` (also names the lease). Page: Accounts > Databases (add form with the advice "use a dedicated read-only user with SELECT only, no REPLICATION"), per database the same "Share with <app>" rows with a route select for Knowledge, Accounts > Database leases with "End lease".
- **Why new tables:** `connect_accounts.source` has a CHECK list (0001). SQLite can only widen it by rebuilding the table; with foreign keys on, the SDK's migration transaction would cascade-delete every child row, and node:sqlite is in defensive mode (no `writable_schema`). Migration 0016 is therefore expand only: three tables and two nullable audit columns.

## External calls and background work

- **External:** `backend.composio.dev/api/v3.1` (key sent only to `*.composio.dev`); Buzz relays chosen by the owner (HTTP query and events with NIP-98 signing); Slack API and Socket Mode; Telegram API; Discord API and gateway; Microsoft Bot Framework (Teams); the catalog artifact from a GitHub release (sha256 verified, cached); user-supplied catalog base URLs and remote MCP servers (https, public addresses only, DNS-pinned, no stdio); the owner's Postgres databases (public addresses only, connected by the checked address, metadata statements only, 0.6.4). No LLM calls. All outbound traffic uses the pinned-connect fetch with a public-address policy (`src/util/net-policy.ts`, `pinned-fetch.ts`).
- **Background:** `onStart` starts channel inbound workers (Slack socket, Discord gateway, Telegram long poll; restart backoff 5 s to 5 minutes), tethers Buzz identities for known agents, and runs a 15 s timer that purges old channel inbox rows and posts due scheduled Buzz posts (claim as `sending`; a stale `sending` over 10 minutes is marked failed and never re-sent; at most 50 scheduled per agent; the agent must still be in the slice and not paused).
